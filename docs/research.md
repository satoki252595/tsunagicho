## 次に試す「構成帳」の事業仮説

利用者は「持っているスマホとマイクで、このアプリに音声を入れたい」のように、手持ちと目的を指定する。結果は接続図・必要な設定・試した機能・確認日と根拠を含む。分からない組み合わせをAIが動作確認済みに変換しない。

初期対象の仮案は**スマホ動画撮影で外付けマイクを使う構成**。キャプチャ、PC、自動車、家電全般まで同時に広げない。以下は構想であり、製品や検証データはまだ作っていない。

| 誰に何を提供するか | 継続利用・対価の仮説 |
|---|---|
| 消費者: 手持ちの構成保存、購入前の確認、使えた手順、更新後に確認が必要な箇所 | 無料。初回から答えに到達できるようにし、追加購入・設定変更時に戻る。毎日使う需要は想定しない |
| 販売店: 商品ページでの構成確認、回答の再利用、未解決問い合わせの把握 | 月額課金。新規集客そのものより、購入前後の問い合わせ工数を減らせるかを売る |
| 検証協力者・店員: 自分の確認記録を再利用できる管理画面と共有リンク | 再回答の手間を減らすことを投稿の動機にする。無償の善意だけで大量の検証が集まるとは仮定しない |

検証価格は仮に**1店舗月4,980円**。確認済み相場や売上予測ではない。仮の人件費を2,000円/時と置くと、月額と同程度になるのは約150分の削減。月50件で各5分減るなら約250分・約8,333円相当だが、対応件数、実際の削減、追加確認工数はすべて未測定である。返品削減は別途、互換問題に起因する返品と分母を測る必要がある。

初期は1店の既存問い合わせと、再利用許諾を確認した確認記録だけで「繰り返し回答を減らす」価値を出す。多人数の参加を初回価値の前提にしない。獲得経路の仮説は、その店の商品ページ・購入案内・既存の機材解説からの導線。広告費0円でも顧客獲得は自動ではなく、最初の協力店との接点は未確認。

### 模倣されにくさが生まれる条件

公開情報は競合も使える。蓄積する核は、利用を許諾された「機材の組み合わせ × OS/アプリ/ファームウェア版 × 配線 × 設定 × 試した機能 × 結果 × 根拠 × 確認日」の記録である。

1. 店舗の実対応で記録を残し、同じ質問に再利用する。
2. 本人・提供元が横断利用を許した記録だけを他の構成確認にも使う。個人情報や店舗の営業情報は共有しない。店が持つ資料だから自由に再利用できるとは扱わない。
3. 同じ機種を扱う別店舗の利用で、既存記録の不足や更新後の変化が分かる。未検証・公式記載・本人報告・再現確認を区別し、食い違いを残す。
4. 対応範囲と回答品質が改善し、次の店舗も初日から使える状態になる。提携店の導線がさらに確認事例を運ぶ。

この循環が実測できた場合に限り、データと流通経路の堀と呼べる。SKUの重なりがない、横断共有の許諾が取れない、虚偽投稿が増える、版ごとの再検証が売上以上にかかる場合は成立しない。データ件数や履歴保存だけをネットワーク効果と呼ばない。顧客が自分の記録を持ち出せないことを強みにしない。

「完全無料の大きなデータをAIに入れれば堀ができる」という前提は置けない。無料情報は確認コストの低減に使い、独自の検証記録と販売導線を作れるかが本体になる。公式情報と検索AIだけで購入判断が完了する用途は対象から外す。

## 既存AI契約をどう使うか

- Grok Bot: ユーザーの依頼ごとに、買い手の困り事・代替手段・支出・反証を調査。今回の調査経路は実機で確認した。取得できないX本文を取得済みと扱わない。
- Codex: 記録設計、ローカルの検索・絞り込み、テスト、GitHubへの資料保存。
- Claude Code / Cursor: 難しい設計や権利条件の読み落としを独立レビューする必要が生じたときに使う。今回これらへの追加レビューは実行していない。
- Gemini: 接続・残枠を確認してから比較調査に使う候補。現時点のCLIは未導入・未検証。

顧客が検索するたびに個人向けAIサブスクを呼ぶ設計にしない。最初の試作品は、事前に検証した少量の記録を通常の検索・絞り込みで返せば足りる。AIは開発・調査・許諾された資料の整形に使い、物理的な動作試験の代役にはしない。Cloudflareの公開構成と包含枠は採用後に確認する。

既存サブスクの固定費、運営者の時間、将来のStripe手数料を消して「利益率100%」とはしない。現在は実決済・有料API・追加機材購入を行わない。

## 本開発へ進む前の最小検証

以下の数字は、この案件の採否を決めるための仮の基準であり、業界基準ではない。期間が過ぎただけ、閲覧が少ないだけでは需要を否定しない。

1. 案を選んだら既存repoを確認し、専用private repoと `/Users/satoki252595/projects/<service-slug>/` を用意する。候補比較中のため、今回はサービスrepoやコードを作っていない。
2. 1つの用途に絞り、利用可能な既存機材と許諾済み資料で5〜10構成の記録を作る。公式記載と実機確認は別表示。実機確認できなければ「未検証」のままにする。
3. 想定利用者10人の具体的な購入・接続課題で、公式リンクだけの場合と構成帳の場合を比較する。答えが出るまでの時間、解決した件数、誤案内、再確認の手間を記録する。画面への好評価だけで採用しない。
4. 対象カテゴリの販売店5店に、既存問い合わせの件数と匿名化・再利用可能な記録の有無を確認する。少なくとも2店が月4,980円という具体価格で試用継続を検討し、1店が計測付き試用に協力することを次段階の仮の条件にする。口頭の賛同、価格付きの意向、実際の購入を区別する。
5. 試用後は注文100件あたりの関連問い合わせ・互換返品、1件の対応時間、検証記録の更新時間を測る。注文構成・季節性・件数不足が違えば因果は断定しない。

公開・外部への試用依頼・連絡は、具体的な画面、依頼文、対象、費用を準備してからユーザーの許可を得る。現在それらは実行していない。

**取り下げ条件:** 公式リンクだけで同等の解決が得られる／提供元の許諾が得られない／共有できる記録が集まらない／販売店の対象問い合わせが少ない／具体価格で継続意向がない／再検証工数が店舗の削減価値を上回る。該当するなら広く実装せず、この候補を外す。
